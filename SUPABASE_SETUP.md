# Подключение каталога DeepSeek к Supabase

Игры, локальный конструктор промптов и прежний прогресс работают как раньше.
Новый каталог и панель используют Supabase. Пока подключение не настроено,
публичный каталог пуст, а `https://veronikaverner777.github.io/promt-child/#admin`
показывает инструкцию, а не незащищённый редактор.

## 1. Создайте проект Supabase

1. Откройте https://supabase.com/dashboard и создайте проект.
2. Дождитесь готовности базы. Пароль базы храните только у себя.
3. В настройках проекта найдите **Project URL** и **API Keys → Publishable key**
   (`sb_publishable_…`). Для старых проектов поддерживается также публичный
   `anon` JWT через `VITE_SUPABASE_ANON_KEY` в локальной среде.

Это публичные настройки браузерного клиента, они будут видны в собранном сайте.
**Никогда не используйте `service_role`, `sb_secret_…`, JWT secret, пароль базы
или персональный токен Supabase в Vite, GitHub Variables или исходниках.**
Сборка отклоняет server-secret и service-role ключи до создания браузерного
JavaScript. Клиент также отказывается с ними работать; права на данные
обеспечивают серверные политики RLS.

## 2. Выполните SQL-схему

В **SQL Editor → New query** скопируйте целиком файл
[supabase/migrations/202611010001_deepseek_catalog.sql](supabase/migrations/202611010001_deepseek_catalog.sql)
и нажмите **Run** от имени владельца проекта.

Скрипт создаёт:

- `prompt_categories` — категории и их порядок;
- `deepseek_prompts` — название, описание, полный текст, теги, путь обложки,
  категория, состояние публикации, порядок и даты;
- `private.admin_users` — список администраторов, недоступный через API;
- функцию `is_admin()` и атомарные функции перестановки;
- RLS для таблиц и приватный Storage bucket `deepseek-covers` с политиками.

Посетители читают только опубликованные промпты. Авторизованные пользователи
без роли администратора не могут редактировать данные, публиковать промпты,
загружать изображения или назначать себе роль. Черновики доступны только
администраторам. Категорию, на которую ссылаются промпты, удалить нельзя.
Скрипт проверен на повторный запуск; существующие строки не удаляются.
Перед применением в уже используемой базе сохраните резервную копию и
проверьте отсутствие сторонних политик с более широкими разрешениями:
PostgreSQL объединяет разрешающие RLS-политики через OR.

## 3. Создайте администратора

1. В **Authentication → Users → Add user → Create new user** создайте аккаунт
   с email и сильным паролем. Подтвердите email в интерфейсе Supabase
   (**Auto Confirm User**), если эта опция доступна.
2. Скопируйте **User UID** созданного аккаунта.
3. В SQL Editor выполните, заменив пример UUID на скопированный UID:

```sql
insert into private.admin_users (user_id)
values ('ВАШ-USER-UID'::uuid)
on conflict (user_id) do nothing;
```

Не добавляйте роль через `user_metadata`: пользователь может менять свои
метаданные. Единственный источник прав — закрытая таблица выше.
Публичного создания аккаунтов на сайте нет. Если другие аккаунты не нужны,
отключите **Allow new users to sign up** в настройках Authentication.

Для удаления административного доступа:

```sql
delete from private.admin_users where user_id = 'ВАШ-USER-UID'::uuid;
```

RLS начинает запрещать запросы немедленно. Уже открытая вкладка панели может
показывать старый интерфейс до обновления, но сервер отклонит новые изменения.

## 4. Настройте URL Auth

В **Authentication → URL Configuration** задайте:

- **Site URL:** `https://veronikaverner777.github.io/promt-child/`;
- при необходимости локального входа добавьте
  `http://localhost:5173/promt-child/` в **Redirect URLs**.

Панель использует вход по email/паролю, не OAuth и не magic links. Сеанс
сохраняется Supabase Auth; автоматическая обработка Auth-данных в URL отключена,
чтобы не конфликтовать с hash-навигацией GitHub Pages. Восстановить пароль
администратора можно через Supabase Dashboard; на публичном сайте отдельного
сброса пароля нет.

## 5. Передайте публичную конфигурацию в GitHub Pages

В репозитории **veronikaverner777/promt-child** откройте
**Settings → Secrets and variables → Actions → Variables → New repository variable**.
Создайте две переменные:

| Имя                             | Значение                                             |
| ------------------------------- | ---------------------------------------------------- |
| `VITE_SUPABASE_URL`             | Project URL, например `https://abcdefgh.supabase.co` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный `sb_publishable_…` ключ                    |

Workflow `.github/workflows/deploy-pages.yml` передаёт их только в шаг
`npm run build`. Для старого `anon` ключа используйте ту же GitHub-переменную
`VITE_SUPABASE_PUBLISHABLE_KEY`: клиент распознаёт публичный `anon` JWT.
Переменные Vite встраиваются при сборке: изменения настроек не меняют уже
опубликованный JavaScript.

После сохранения кода через Pull Request в `main` запустите или перезапустите
**Actions → Publish AI PLAYGROUND to GitHub Pages → Run workflow → main**.
Убедитесь, что **Settings → Pages → Source** установлен в **GitHub Actions**.
Переименовывать репозиторий не нужно; Vite base остаётся `/promt-child/`.

## 6. Проверьте вход и первую публикацию

1. Откройте `https://veronikaverner777.github.io/promt-child/#admin`.
2. Войдите email и паролем созданного администратора.
3. Нажмите **Категории**, добавьте первую категорию.
4. Нажмите **Создать промпт**. Заполните название, категорию, описание,
   полный текст и теги; при желании добавьте обложку.
5. Проверьте карточку справа и нажмите **Предпросмотр** для полного текста.
6. Нажмите **Сохранить** — появится черновик.
7. В списке нажмите **Опубликовать**. Промпт появится на главной и в
   `https://veronikaverner777.github.io/promt-child/#prompts`.
8. Откройте этот каталог в приватном окне: опубликованный промпт доступен,
   черновик — нет. В панели проверьте редактирование, перестановку стрелками,
   снятие с публикации и удаление.

В этой вкладке каталог обновляется сразу после действий администратора.
Другие открытые вкладки проверяют обновления каждые 30 секунд и при возврате
фокуса. Пересборка Pages при добавлении промптов не требуется.

Обложки сохраняются в приватном Storage. Допустимы JPG, PNG и WebP до 5 МБ,
не больше 6000 × 6000 пикселей; SVG запрещён. Для опубликованных карточек
создаются ссылки сроком 5 минут, которые обновляются вместе с каталогом.
Уже выданная ссылка на обложку после снятия с публикации может действовать
до истечения этого срока. Сам текст неопубликованного промпта API не отдаёт.
При ошибке сохранения новая загруженная обложка удаляется по возможности;
при сетевых сбоях остаточные файлы можно удалить в Storage Dashboard.

## Локальная разработка и проверки

Скопируйте `.env.example` в `.env.local`, заполните **только публичные** URL
и ключ. `.env.local` и другие `.env`-файлы исключены из Git. Перезапустите Vite.
Не отправляйте пароли или ключи в чат.

```bash
npm ci
npm run dev
npm run build
npm run test:security
npm run test:e2e
```

Без параметров Supabase работают существующий сайт, игры и безопасный экран
настройки панели. Для UI-тестов интеграции используются изолированные тестовые
ответы Supabase, а SQL/RLS проверяется настоящим PostgreSQL в PGlite с локальными
заменами окружения Auth/Storage. Эти проверки не подтверждают подключение к
вашему облачному проекту: после шагов выше обязательно выполните проверку
из пункта 6 на своём Supabase.

Если среда Codex ограничивает сеть, разрешите точный домен вашего проекта
`<project-ref>.supabase.co` в её сетевых настройках. Из браузера посетителя
Supabase вызывается напрямую по HTTPS. Следите за лимитами и резервными копиями
в Supabase Dashboard.
